# BFR Macro & Tracking Utility — v2.0.5 Development Roadmap

**Status:** Active planning and investigation  
**Development branch:** `develop/v2.0.5`  
**Verified starting commit:** `4b112cf89db0da3ac74efa01a7594662c3a0d247`

**Primary feature:** Reliable unit-drop and material-drop tracking in Run History

## Goals and guardrails

The main v2.0.5 feature is to record unit and material rewards attributable to each completed dungeon run or repeat batch, and make those rewards understandable in Run History.

- Keep v2.0.4 unchanged.
- Keep all v2.0.5 work on `develop/v2.0.5` until release approval.
- Preserve existing settings, macros, logs, WebView2 profile and Run History.
- Preserve the Tauri application identifier and existing history compatibility.
- Extend the existing tracker rather than introducing a second network-observation subsystem.
- Do not infer drops from inventory snapshots unless no authoritative reward source exists and the limitations are explicit.
- Do not send modified requests to game endpoints, bypass authentication, or store credentials, cookies or tokens.
- Do not add unverified API fields or fabricate zero-drop results.
- Complete each stage and review its evidence before proceeding to the next stage.
- Do not reopen the completed v2.0.4 roadmap or its Stage 4 performance benchmarking.

## Stage 1 — Reward API evidence and semantics

- Preserve response structure and field types in a separate `Logs/reward-api-samples.json` export; do not mix samples into Run History.
- Redact common credential and account-identifying fields in Rust before persistence.
- Bound capture size and retain only the latest 40 samples.
- Provide an **API Samples** shortcut in the Run History window to open the Logs folder.
- Do not modify requests, replay calls, or collect request headers, cookies, or credentials.

The in-app capture implementation still requires automated build/test verification and hands-on gameplay validation before it is considered complete.

Objective: Establish which response fields represent actual rewards awarded by a battle, rather than the player's current inventory.

Investigate:
1. Successful single-run `/api/battles/finish` response.
2. Successful repeat `/api/battles/repeat` response, including intermediate and final batch snapshots.
3. Exact locations and data types for unit rewards and material rewards.
4. Whether reward entries are IDs, objects, arrays, or quantity maps.
5. Whether arrays represent newly awarded drops, inventory snapshots, or another concept.
6. Whether repeat response item data is per-chunk or cumulative.
7. Whether a stable batch/run identifier exists for safe deduplication.
8. Whether item metadata (name, category, icon) is available through a documented or safely observable game resource.

Evidence requirements:
- Sanitized representative JSON structures from normal gameplay.
- Remove cookies, authorization headers, session IDs, tokens, account identifiers and unrelated personal data.
- Preserve field names, value types, array/object shapes and example quantities.
- Do not modify or replay authenticated requests.
- Do not infer endpoint semantics from field names alone.

**Gate:** No drop-capture implementation until the data semantics are supported by observed examples.

If the game does not expose authoritative drop data, document the limitation and compare safe alternatives before implementation.

## Stage 2 — Drop schema and normalization

Objective: Define a backward-compatible data model.

Proposed logical fields:
- `unit_drops`: optional list/map of stable unit IDs and awarded quantities.
- `material_drops`: optional list/map of stable material IDs and awarded quantities.
- Optional source/quality marker where needed to distinguish confirmed rewards from incomplete data.

Design requirements:
- Preserve raw stable IDs; do not depend on display names as identifiers.
- Validate item IDs, categories, quantities, record size and entry count.
- Keep new fields optional so old JSONL records remain readable.
- Preserve unknown IDs rather than discarding valid but unrecognized rewards.
- Treat missing data as unavailable, not as zero.
- Define repeat-batch delta/cumulative rules using verified response semantics.
- Prevent repeated cumulative snapshots from double-counting.
- Avoid changing existing Zel/Karma/Honor/EXP/run-count accounting.

Tests:
- Valid unit and material entries.
- Unknown IDs.
- Missing, null, malformed and unexpected data types.
- Duplicate entries and duplicate snapshots.
- Cumulative repeat updates and final batch.
- Backward compatibility with existing history records.

**Gate:** Review the schema and test cases before wiring it into persistence.

## Stage 3 — Capture and persistence

Objective: Extend the existing same-origin reward observer and Rust persistence path.

Tasks:
1. Add only the confirmed response fields.
2. Keep observation restricted to verified same-origin game reward responses.
3. Reuse existing tracker IPC and persistence protections where practical.
4. Validate all new fields again in Rust; never trust page-side normalization alone.
5. Persist unit/material rewards with the corresponding run or repeat-batch snapshot.
6. Ensure batch updates replace/select the correct cumulative state rather than summing snapshots.
7. Keep deduplication stable across application restarts.
8. Preserve current diagnostic privacy and rate limits.
9. Handle partial, missing and unknown reward data safely.

**Gate:** Tests must demonstrate correct single-run and repeat-batch accounting before UI work.

## Stage 4 — Run History presentation

Objective: Display useful drop information without making the table unwieldy.

Preferred UI:
- A compact Drops summary in each completion row.
- Expandable details grouped into Units and Materials.
- Item name and quantity, with icon only when verified metadata is available.
- A clear unavailable/incomplete indicator when the source does not provide reliable data.
- Unknown item IDs remain inspectable rather than silently omitted.

Preserve:
- Existing search and pagination.
- Newest-first ordering.
- Individual deletion and Clear All behavior.
- Existing table accessibility and horizontal-scroll behavior.
- Correct display of old records without drop fields.
